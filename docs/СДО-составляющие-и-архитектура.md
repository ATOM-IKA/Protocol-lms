# СДО / LMS — составляющие и архитектура (часть 1)

Структурированный конспект по разработке системы дистанционного обучения:
правовая база, инфраструктура, ПО, безопасность, архитектура и связка «личный кабинет ↔ СДО».

---

## 1. Правовая база (РФ)

- **ФЗ-273 «Об образовании в РФ»** — ст. 16 о понятии электронного обучения (ЭО) и дистанционных образовательных технологий (ДОТ).
- **Приказ Минобрнауки № 816** — порядок применения организациями ЭО и ДОТ.
- **Постановление Правительства РФ № 1678** (от 11.10.2023) — правила применения ЭО.
- **ФЗ-152 «О персональных данных»** — защита ПДн учащихся и сотрудников.
- **Локальные нормативные акты** организации — устав, положения об ЭО, регламенты работы в СДО.
- **Авторские права** — условия доступа и лицензии на используемый контент.

На практике важно учесть: идентификацию обучающихся (при аттестациях), электронную информационно-образовательную среду (ЭИОС), доступность для людей с ОВЗ, защиту ПДн, сроки хранения и право пользователя запросить/удалить свои данные.

---

## 2. Инфраструктура (где всё живёт)

- Серверы или виртуальные машины — для бэкенда, БД и компонентов.
- Операционная система (Linux, Windows Server).
- Хостинг, домен, SSL-сертификат — вход по HTTPS.
- Отказоустойчивость: резервные мощности, ИБП, система резервного копирования.

---

## 3. Программная основа

- **СУБД** — PostgreSQL, MySQL, Oracle и др.; здесь хранятся пользователи, курсы, тесты, статистика, логи. Заранее продумать схему и связи таблиц.
- **Сервер приложений** — бизнес-логика: авторизация, проверка прав, формирование отчётов.
- **Веб-сервер** — Apache / Nginx; принимает запросы браузеров и передаёт серверу приложений.
- **Стек технологий** — языки (Python, Java, PHP, JS), фреймворки, библиотеки.
- **Инструменты разработки** — среды проектирования интерфейсов, системы контроля версий, инструменты тестирования.

---

## 4. Архитектура и модули

- Продуманное взаимодействие модулей: управление пользователями, загрузка курсов, тестирование, аналитика, интеграция с внешними системами (HRM, CRM, ERP).
- Часто — сервис-ориентированная архитектура (изоляция функций).
- **Опциональные модули**: создание курсов, авто-проверка заданий, вебинары, совместная работа (форумы, чаты), генерация отчётов.
- **API для интеграции** — обмен данными с другими сервисами.
- **Технические стандарты** — SCORM (Sharable Content Object Reference Model) для упаковки и переноса учебного контента между LMS.
- **Масштабируемость** — стабильная работа и при малой, и при растущей нагрузке.
- **Тестирование** — обязательно нагрузочное.

---

## 5. Безопасность

- Аутентификация (пароли, токены, многофакторная), авторизация (разграничение прав).
- Шифрование данных при передаче (HTTPS/TLS) и при хранении.
- Защита от угроз: DDoS, XSS, SQL-инъекции.
- Протоколирование (аудит) ключевых действий: вход, прохождение теста, загрузка задания.
- Для повышенных требований (госзаказ, ПДн особой категории) — ГОСТ-шифрование и сертифицированные СКЗИ. Для большинства вузов и корпоративных LMS достаточно HTTPS + OAuth2 + разграничение прав.

---

## 6. Ролевая модель

- Администратор, преподаватель, студент, куратор — у каждой роли свой набор прав на чтение/запись. Определить заранее.

---

## 7. Идеология: единая точка входа, разные зоны ответственности

- **Портал / личный кабинет** — «лицо» проекта: маркетинг, публичные страницы, навигация, витрина профиля студента (ФИО, статус, контакты, документы). Здесь **не** хранят учебные результаты и не запускают тесты.
- **СДО / LMS** — «учебная зона»: курсы, тесты, прогресс, оценки, журналы. Знает о студенте только минимально необходимое.
- **Передача данных** — только по защищённому каналу, в зашифрованном виде, по запросу, с проверкой прав. Никаких «сливов» всей базы. Это сразу закрывает ФЗ-152: минимум данных в каждой системе, контроль доступа, аудит.

---

## 8. Архитектурные компоненты

1. **Frontend-портал** (страница + личный кабинет) — React / Vue / Next.js; UX, публичные страницы, профиль, вход.
2. **IAM / SSO** (Keycloak, Auth0, самописный на OIDC/OAuth2) — учётные данные, токены, роли.
3. **Backend-шлюз (API Gateway)** — точка входа для всех запросов: проверка токена, логирование попыток доступа, лимиты.
4. **СДО / LMS** — готовое решение (Moodle, Open edX) либо самописное ядро; отдельный сервис.
5. **База данных студентов** — в IAM или в отдельной БД (ПДн и атрибуты профиля).
6. **Шина / очередь событий** (опционально) — события вида «студент зачислен» без прямого запроса к СДО.

---

## 9. Связка «личный кабинет ↔ СДО»

**Вариант A — SSO + передача идентификатора** (проще, чаще используется):

1. Студент заходит на портал, авторизуется в IAM.
2. IAM выдаёт JWT-токен с правами и идентификатором студента (UUID, не ФИО/паспорт).
3. При переходе в СДО портал делает редирект с токеном или меняет его на сессионный токен СДО через бэкенд.
4. СДО проверяет токен у IAM, получает только идентификатор и роль.
5. СДО по ID подтягивает минимальный профиль (имя, email) из своей БД или запрашивает у IAM по защищённому API.

Плюсы: быстро внедрить, готовые интеграции (Moodle/Open edX), данные по HTTPS, токены с коротким сроком жизни, без передачи паролей.

**Вариант B — API-запрос «по требованию»** (более строгий контроль):

1. Личный кабинет при необходимости запрашивает данные у СДО через API.
2. API проверяет права (роль, scope), логирует запрос.
3. СДО возвращает только разрешённый набор полей (например: курс, прогресс, дата последнего входа).
4. Обратно в личный кабинет ничего не передаётся: профиль живёт в IAM, а не в СДО.

Подходит, если нужно чётко разделить зоны: профиль — в одном месте, обучение — в другом.

---

## 10. Правильная передача данных в зашифрованном виде

Ручное «шифрование строки с ФИО» — антипаттерн. Правильная схема:

1. **HTTPS (TLS)** — обязательное шифрование канала; все запросы портал ↔ IAM ↔ СДО по HTTPS.
2. **Токены доступа (JWT / OAuth2)** — вместо логина/пароля передаётся подписанный токен (подпись гарантирует неподдельность).
3. **Минимальные данные** — передавать только ID студента и роль; имя и email подтягивать отдельно и только при реальной необходимости.
4. **Шифрование на уровне БД** — если хранятся ПДн: TDE или шифрование отдельных полей.
5. **Логирование** — каждый запрос к данным студента фиксируется (кто, когда, зачем) — для безопасности и ФЗ-152.

---

## 11. Что обязательно включить в ТЗ / архитектурное описание

- Единая аутентификация (SSO) на базе OAuth2 / OIDC.
- Разделение данных: профиль — в IAM, учебные данные — в СДО; передача только по API, без дублирования всей карточки студента.
- HTTPS везде, запрет HTTP.
- Ролевая модель: администратор, преподаватель, студент, куратор — у каждой свои права.
- Логирование доступа к ПДн: кто и когда запрашивал профиль или результаты студента.

# Часть 2 — дополнения

## 12. Минимизация передаваемых данных

- Между системами передавать минимум: **ID, роль, иногда имя/email**.
- Паспортных данных в СДО быть **не должно**, если это не требуется для юридически значимой аттестации.

## 13. Резервное копирование и восстановление

- Регламент: где и как хранятся бэкапы, как быстро можно восстановить систему после сбоя.

## 14. Готовая формулировка для команды / ТЗ

> «Мы делаем единую точку входа (портал + личный кабинет) и отдельную учебную систему (СДО). Авторизация — через IAM с OAuth2. При входе в СДО используется SSO: IAM передаёт только идентификатор студента и роль в зашифрованном канале (HTTPS). СДО запрашивает минимально необходимые данные профиля по API. Все запросы к персональным данным логируются. Такой подход обеспечивает соответствие ФЗ-152, упрощает поддержку и позволяет масштабировать системы независимо друг от друга.»

## 15. Блокчейн для ПДн (если рассматривается)

- Реализовать можно, но с оговорками и под 152-ФЗ. Обычно — **гибридный подход**: не хранить ПДн (ФИО, паспорт, email) прямо в блокчейне.
- Данные шифруют и хранят во внешнем изменяемом хранилище (БД, облако с контролем доступа), а в блокчейн пишут только **хеш** (отпечаток) и, возможно, цифровую подпись.
- Проверка целостности: текущие данные прогоняют через ту же хеш-функцию и сравнивают с записью в блокчейне.
- Даёт: безопасность (без ключа — «мусор»), целостность (данные не подменили), аудит (прозрачная цепочка).
- **Право на забвение (152-ФЗ)**: неизменяемость блокчейна конфликтует с правом на удаление. Решение — хранить ПДн во внешнем хранилище, в блокчейне только хеши; для «удаления» стереть внешнюю запись (по хешу восстановить нельзя).
- При шифровании ПДн в РФ часто нужны **сертифицированные СКЗИ** (алгоритмы ГОСТ). Практические советы: не переусложнять, продумать управление ключами, провести аудит угроз.

## 16. LMS vs СДО — функционально совпадают

Оба закрывают одинаковый набор задач: управление пользователями и ролями, загрузка/структурирование контента, контроль и оценки (тесты, задания, дедлайны), отслеживание прогресса и отчёты, коммуникации (чаты, форумы, уведомления), интеграция с внешними системами.

Термин выбирают под аудиторию:

- **Вуз / госзадание** → термин **СДО**, явные ссылки на ПП №1678 и ФЗ-152 (фиксация действий, идентификация, логи, обработка ПДн).
- **Корпоративная / международная система** → термин **LMS**, упор на автоматизацию, аналитику, интеграции.

Архитектурно это одна платформа: ядро обеспечивает и управление (LMS-логика), и дистанционный доступ (СДО-функционал), плюс безопасность и соответствие законам.

## 17. Админ-часть (специфика колледжа/СПО)

- **Ролевая модель**: помимо супер-админа — администратор системы (настройки, пользователи, интеграции), методист (курсы, учебные планы), преподаватель (материалы, задания, оценки), студент; для СПО критичны **родители несовершеннолетних** (отдельный кабинет). Не давать лишних прав.
- **Управление пользователями**: массовое добавление студентов/педагогов, назначение ролей, групп, потоков; импорт из существующей базы (1С:Колледж, региональный электронный журнал).
- **Работа с контентом**: загрузка лекций, тестов, практических; **версионирование** материалов (откат изменений).
- **Интеграции**: электронный журнал, система учёта контингента, видеоконференции.
- **Настройки безопасности**: пароли, 2FA, шифрование трафика; отдельно — контроль доступа к чувствительным данным (результаты аттестации).
- **Резервное копирование**: регулярное сохранение бэкапов.

## 18. Аудит (специфика колледжа)

- **Аудит действий пользователей**: логирование ключевых событий (вход/выход, создание/редактирование курса, отправка заданий, изменение оценок, доступ к конфиденциальным разделам); анализ логов для нарушений, узких мест, доказательств в спорах.
- **Аудит соответствия**: ФГОС СПО, ПП №1678, внутренние регламенты; фиксация хода образовательного процесса, портфолио, синхронное/асинхронное взаимодействие.
- **Аудит безопасности**: права доступа, сложность паролей, «запасные» неиспользуемые учётки.
- **Аудит эффективности**: метрики — доля активных курсов, процент дошедших до конца, использование инструментов преподавателями.
- **Планирование**: график аудитов (раз в квартал / перед новым учебным годом), зафиксированные критерии.
